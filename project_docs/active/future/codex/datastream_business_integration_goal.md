Goal: Plan how to make the Datastream platform useful to business teams by connecting its landing hub, analysis tools, Slipstream document evidence, and Context Ledger governed context in one self-service pilot.

This is a deferred planning prompt. When the user promotes it, prepare an implementation roadmap from the current repositories and verified contracts. Start from the existing platform hub and Devstream workflows. Keep the repositories and their ownership boundaries in place while the pilot tests what should be shared.

## Start with the existing platform

Read the [execution status](../../status/project_execution_status.md), [active gate](../../active_gate/README.md), and [three-project platform review](three_project_data_platform_review.md). Verify the actual hub, Data Hub, saved datasets, Data Model and Business Objects, and the Analytics and BI-first AI Chat entry points. Trace how the [saved dataset API](../../saved_datasets/README.md), [workspace contract](../../contracts/multiple_data_source_workspace.md), and [governance and lineage contract](../../contracts/data_catalog_lineage.md) carry `dataset_id`, `revision`, `source_id`, `workspace_id`, `analysis_context`, `analysis_lineage`, and `governance_readiness`. Establish which identifiers and revisions can cross application boundaries and which require mapping or additional contracts. Check the current Slipstream and Context Ledger contracts linked by the platform review. For each proposed capability, name its owner and tell the reader whether the relevant behavior is verified or proposed.

## Design one business workflow

Use one business domain, one structured source, one document collection, and one curated data product tied to related business objects. A business user starts at the hub, finds the product by a familiar term, sees its owner, coverage, and freshness, and requests access or opens an approved workspace. They explore an agreed measure in Devstream without code and can follow a material result to contributing rows or an exact Slipstream passage when permitted. A second team can reuse the same published revision in its own authorized scope. Show what happens after an input refresh and after access is revoked. Measure time to a first usable result and time to verify a figure against the teams’ existing workflow.

Give builders a path to register and prepare the inputs, define the measure once in the semantic model, review source evidence, and publish a maintained revision. Keep the business view focused on discovery, access, and exploration. Describe workspace provisioning as a short form with the requested scope, approval outcome, and visible status. Define the pilot roles, ownership, and isolation model from onboarding through revocation.

## Recommend the integration and access model

Compare launch links, supported adapters, and direct integration for each companion app. Recommend the shallowest integration that delivers the pilot and justify it using actual contracts and ownership. Specify who owns each source and contract, how subject and product identities are resolved, how requests and evidence references are versioned, and what users see when a service fails or a revision is unavailable. Keep links to original evidence and distinguish pinned revisions from current data. Use an approved copy only when the workflow requires one.

For the pilot, propose how organizational SSO, role mapping, workspace isolation, dataset access, and row-level restrictions where required will be enforced at trusted service boundaries. Apply current permissions to discovery, previews, Analytics, AI Chat, evidence links, caches, and exports as applicable. Define permitted metadata for a restricted product, what gets audited, and the behavior for expired or revoked access. Treat these as launch requirements for shared data. Stage broader stewardship, quality and publishing controls as usage grows.

Recommend how to extend the current catalog, workspace provisioning, identity and policy enforcement, existing frontend, and storage. Decide whether raw, refined, and curated represent catalog stages or require storage changes for the pilot. Explain the fit with the current stack, the operational cost, and the conditions that would justify a new service or cloud dependency.

## Return an executable roadmap

Provide a proposed folder and ownership map within the existing repositories, the first three components to build in order, the recommended technical approach for each layer, and the unresolved decisions that affect implementation. Start from shared identity, permissions, and product/evidence contracts where the flow depends on them. Then sequence one end-to-end integration and the self-service business experience. Include target files, contract changes, and focused verification commands for each component. Acceptance must cover an approved user, a restricted user, access revocation, revision refresh, and a companion-app outage. Use fixtures for automated verification and leave final browser acceptance to the user in chat. Return the first bounded implementation goal for review. Source changes begin only when the user authorizes that implementation.
